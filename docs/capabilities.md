# ADR 002: Capability registry, discovery and individual approvals

Date: 2026-10-19. Scope: native telemetry, notification measurements, standardized history, plugin feature/OpenAPI discovery, explicitly approved GET and POST invocation and individually approved native PUTs from issue #30. Every plugin GET, POST and native PUT requires its own saved administrator approval, alongside native Signal K permissions; there is no blanket approval. Built-in data reads use native permissions without that extra review. The published first alpha predates native PUT support.

## Architecture

`src/capabilities/registry.ts` owns capability lookup, descriptions and execution. Dedicated tools delegate to that registry, so generic calls cannot bypass the telemetry ACL implementation. Every entry requires an authenticated, recognized Signal K principal; asynchronous work rechecks identity before returning. Disabled/stopped plugins cannot admit new work, and active HTTP requests are aborted on stop/disconnect/deadline.

`getFeatures()` is the public feature inventory. Plugin IDs are native `plugin.id` values, which can differ from npm package names and include uppercase letters (for example, `AdvancedWind`). Discovery, OpenAPI URLs, routes and approvals preserve their exact case; a differently cased ID does not inherit approval. We project API names and plugin IDs/enabled state, exclude our own plugin, bound the inventory, and report discovery failure without disabling core telemetry. Plugin descriptions are loaded on demand from `/skServer/openapi/plugins/:pluginId`. This uses the server's HTTP discovery surface instead of reading `pluginsMap` internals. The seven supported native namespaces use the same OpenAPI parser and executor; other advertised namespaces remain non-executable.

A GET OpenAPI operation is executable only when its plugin is enabled, its operation ID is unique, its schema is supported, and configuration matches the plugin ID, operation ID, GET method and exact path. Approval can be an existing exact manual entry or a saved native review matching the operation, input schema and description. Duplicate configuration approvals and recursive approvals for this plugin are invalid. Unknown operations, unsupported mutation methods and unsupported schema features stay disabled. POSTs use their own saved endpoint-contract reviews; see [POST contracts](plugin-posts.md). Documentation is untrusted data, never instructions or proof of read-only behavior. An approval must follow review of the actual handler, including side effects and data-level authorization.

`src/capabilities/http.ts` issues bounded GETs for data access, individually reviewed plugin POSTs and fixed-route native PUT/status requests for individually approved actions, back to the socket address/port that accepted the MCP request. It forwards the original bearer token, an Accept header and, for PUTs, a JSON content type and validated value/source body. It follows no redirects, does not fetch external schema references, ignores OpenAPI `servers`, and never uses caller Host/proxy headers to select a destination. Native plugin-route authorization is therefore exercised as the original caller, without a minted plugin/admin token. TLS verification is never disabled. The optional `localTlsServerName` supplies the TLS verification name and SNI without changing the socket destination. Non-TCP hosting and certificate failures fail closed; see [hosting](hosting.md).

Gateway approval is not a promise that the target route will accept the caller. Signal K may impose a stricter permission. Conversely, generic plugin output cannot automatically be translated into telemetry ACL checks; an approved provider remains responsible for its endpoint's data authorization. The test fixture explicitly proves both target ACL and admin-route enforcement.

## Resources boundary

`api.resources` implements native Resources collection/provider discovery and reads for routes, waypoints, regions, notes, chart metadata and logentries. It uses the caller's token through native HTTP routing and forwards provider results unchanged. Measurement tools retain their own ACL checks. Collection-specific input schemas, current provider discovery and bounded responses govern these reads; unknown custom collections remain discoverable without becoming executable. See [Resources operations, query contracts and verification](resources.md). Resource create/upsert/delete use separate saved method/collection/provider/body-contract reviews through the same native admin table, then native Resources HTTP write checks. Telemetry action approval never substitutes for resource approval.

## History boundary

The standardized History route in the inspected 2.33.0 runtime selects a provider and passes parsed query parameters to it; it does not carry a user principal into that provider or check telemetry ACLs. We therefore authorize explicit path/source filters before querying and again on response. Unfiltered queries require native `anyACLs()` to return literal `false`; unknown state or configured ACLs deny the request. Optional response `$source` must agree with a supplied filter when present, but its absence is valid. Context, range, column identity/method and row dimensions/timestamps are validated. The provider JSON is then returned unchanged, including optional metadata and bucket timestamps that may precede the requested start. Conflicting or unexpected columns and extra row cells are rejected. Inputs, time buckets, rows, bytes and timeouts are bounded. Queries use the standard HTTP API with the original bearer and a provider ID obtained from the provider inventory.

The server's expression sanitizer removes hyphens even though source IDs can contain them. We reject unsupported expressions rather than silently changing identifiers. A future upstream fix or separately verified direct-provider adapter is needed to broaden support. No direct InfluxDB queries or guessed source provenance are used. Provider work may continue after HTTP cancellation; the gateway cannot cancel an upstream implementation that does not support it.

## Notifications boundary

The released `/signalk/v2/api/notifications` collection is distinct from the proposed `/signalk/v2/api/alerts` subsystem. The adapter uses only the collection GET with the original bearer, including for single-record lookup. It does not depend on pending upstream PRs, enable core management, or call any lifecycle action. Legacy `signalk.notifications/list` remains separate from `list_notifications` and `get_notification`; both new operations share the dedicated MCP tools' implementation.

In the inspected 2.32.0 and 2.33.0 packages, collection records contain `context`, `path` and `value`. They omit the source and do not apply telemetry ACLs per record. Native integration reproduces this by showing that a denied record is present in the direct GET response but absent from the MCP result. HTTP authentication alone is insufficient.

After fetching, the gateway reauthenticates and checks each record using Signal K's own `checkACL` with its context, notification path and source. Empty native context and the server's own context resolve to `vessels.self` for authorization only; the forwarded context is unchanged. Other valid contexts keep their own ACL scope. Without configured ACLs, a literal native `anyACLs() === false` plus a read grant suffices. Otherwise the adapter uses public `getPath()` to find source provenance by exact equality of the complete registry value with current/source-specific model values. Every matching source must be allowed. It does not guess a source from an ID, accept a caller-provided source assertion, or treat an empty-source grant as access to all sources. Admin identities still pass the same ACL checks.

Records with no matching model value/source, unknown context, changed values or denied source matches are omitted. This can omit older records no longer represented in the model; that is an explicit limitation, not evidence of an empty native registry. Source-specific model entries are bounded to 256 per path. No omitted-record count or denied ID is returned. Absent and denied single-record lookups return the same `NOTIFICATION_UNAVAILABLE` error.

Records are forwarded without field projection or mutation. Optional `value.id`, status, position, creation time and source/timestamp fields are neither required nor synthesized. With core management disabled, the server's collection can use path-based or handler-supplied keys and omit core status; single-record lookup still works through that collection even though native `GET /:id` returns 501. IDs never enter the upstream URL. The adapter bounds the collection to 20,000 entries and the existing HTTP 256 KiB/5-second limits, sorts authorized IDs and applies offset/limit pagination (up to 64 records). Pagination is not a stable snapshot.

Registry paths accept parentheses in provider sensor names, such as `notifications.sensors.SwitchBotTH_(temp1)-AA-BB-CC-DD-EE-FF`. Authorization and model lookup use the exact original path. Empty segments, prototype-related segments, wildcards, brackets, slashes and control characters remain invalid, and paths remain limited to 256 characters. This registry-specific validation does not broaden telemetry, History or native PUT inputs.

`describe_capability` probes registry reads and reports unavailable/invalid upstream responses on those two operations while leaving the legacy operation enabled. The Notifications API has an open strict-OpenAPI-validation issue; this explicit adapter does not parse that document or infer permissions from it. No raise, acknowledge, silence, clear or update action is exposed.

## Native approval requests

`execute_capability` queues an eligible unapproved read only after native authentication, enabled-provider discovery, supported OpenAPI validation and argument validation. It returns `APPROVAL_PENDING` without invoking the target. Discovery alone does not queue anything. Only bounded operation metadata is retained, deduplicated across callers; no request arguments, identities, tokens or response data are saved.

The plugin's dynamic JSON schema supplies pending and saved review metadata to a custom table embedded in native Plugin Config. The table reads the host's plugin inventory, stages Accept/Reject and access edits, and permits deletion only for plugins absent from that inventory (not merely disabled). It rechecks missing-plugin status and concurrent edits before saving. Rejected rows stay editable. The schema remains available to native clients. The host's existing admin-only configuration route saves decisions and restarts the plugin; the MCP route cannot save or approve them. Unsaved entries are memory-only and may be lost on restart or a stale settings save. Saved pending/rejected/approved entries count toward the 64-entry limit. Removing a saved review from plugin configuration revokes its grant and makes it eligible for another request. Keep manual approvals in mind when removing a review; a matching explicit rejection overrides them.

A SHA-256 key binds plugin ID, operation ID, GET path, parsed input schema and displayed description. This is metadata binding, not proof of a provider's implementation or installed version. Changed schema/route/description requires a separate review. Manual approvals retain their existing compatibility behavior; unsupported schemas and collisions remain disabled for all approval types. Admin-only review permissions never bypass the original caller's native route/data permissions.

## Shared native OpenAPI operations

The registry also discovers Course, Weather, Autopilot, Radar, BLE, Tracks and Sensors through the same parser and executor, using fixed native namespace metadata. Generic reads and mutations need individual saved review; HTTP routing forwards the original caller token and leaves endpoint data authorization to Signal K and its provider. Static native documents are cached per gateway lifecycle; plugin contracts, feature inventory, approvals and results remain live. See [native API coverage and verification](native-apis.md).
